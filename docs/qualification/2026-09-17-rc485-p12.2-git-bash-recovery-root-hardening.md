## Real-host failure class

Windows/Git Bash deployment still stopped after `.env` creation with:

```text
ERROR: Use an absolute Windows drive path, such as C:/Users/name/.mreader/database-protection.
```

The previous repair covered `C:/...`, backslash and `/c/...` forms plus direct `HOME` fallback. Further audit found two additional real-host cases that were not covered: Cygwin-style `/cygdrive/c/...`, and shells where `USERPROFILE` is empty or non-drive while `HOME` is also not directly convertible to a Windows drive path. All backup/restore/readiness/startup callers already use the same central recovery-root resolver, so the correct fix is central rather than per-script.

## Repair

`1d17ce50604001f8e6462c8492ccc9582353f4a5` adds one shared Windows path canonicalizer that accepts backslash, `/c/...` and `/cygdrive/c/...` drive forms. On Windows/Git Bash, when the inherited `USERPROFILE` is empty or not a usable drive path, `resolve-db-protection-root.sh` queries native `%USERPROFILE%` through `cmd.exe` with `MSYS_NO_PATHCONV=1` so Git Bash cannot rewrite `/d` or `/c` switches. Manual `.env` roots remain supported and are canonicalized to `C:/...`.

The following shell entry points continue to consume this one resolver rather than duplicate Windows path logic: bootstrap, hybrid-up, hybrid validate/stateful-up, local pre-upgrade backup, P09.4 readiness/runtime gate, PostgreSQL backup/restore/replication setup, and catalog recovery.
