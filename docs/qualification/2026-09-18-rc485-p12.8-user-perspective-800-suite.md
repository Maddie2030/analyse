# RC4.85 P12.8 — user-perspective 800-case qualification suite

Date: 2026-09-18

## Goal

Turn the existing diagnostics, API, integration and browser coverage into one portable qualification command that can be run against the current Docker Desktop twin-plane deployment from the user's machine. The requested acceptance view is user/admin behavior, not a synthetic test-count target.

## Command

```bash
./test-mreader.sh --user-800 \
  --admin-username <disposable-admin> \
  --admin-password <disposable-password> \
  --scraper-series-url <real-public-series-url>
```

The password is not written into the qualification report. Environment variables are preferred when command history is a concern:

```bash
export MREADER_TEST_ADMIN_USERNAME='<disposable-admin>'
export MREADER_TEST_ADMIN_PASSWORD='<disposable-password>'
export MREADER_DIAGNOSTICS_SERIES_URL='<real-public-series-url>'
./test-mreader.sh --user-800
```

## Container execution model

The portable qualification is intentionally **container-first**. The host shell only orchestrates Docker/Kubernetes and collects artifacts; it does not execute the functional API suite with host Python.

- `mreader/api-tests:<version>` is built from `tests/api/Dockerfile` and contains the complete pytest runtime and API test sources.
- `mreader/diagnostics:<version>` is built from `tests/diagnostics/Dockerfile` on top of the API-test image. A dedicated diagnostics container joins the stateful Docker network and executes route audit, collection, PostgreSQL permissions, gateway boundaries, the full core API/functional/integration suite, and optional real external scraper tests against the running user/admin gateways.
- `mreader/browser-tests:<version>` is a separate pinned Playwright container for real user/admin UI journeys.

The API container writes per-test JSON, per-module JSON, `http_exchanges.jsonl`, `journey_actions.jsonl`, stage logs, and JUnit XML for core API, permission, boundary, and external scraper layers. These artifacts are mounted onto the host under the run-specific `test-results` directory and feed the consolidated diagnostic/qualification report. This is the evidence used for defect debugging and re-test; a host dependency problem must not be mistaken for an application failure.

## Coverage model

The runner executes more than 800 cases and produces an exact 800-case accountability ledger. Functional API, external scraper and browser E2E evidence are selected first, followed by user/admin gateway boundaries and PostgreSQL least-privilege checks. The overall qualification result still fails if any executed case outside the canonical 800 fails.

## P12.8 repairs

1. **Functional pytest diagnostics were not running.** `tests/diagnostics/runner.py` used the first `-m` in `python -m pytest ... -m <marker>`, replacing the literal `pytest` module name with the marker expression. The old diagnostic therefore collected 1,255 cases but executed zero core functional API cases. P12.8 locates only pytest's marker `-m`, preserving `python -m pytest`.
2. **Admin database UI smoke had a strict-locator collision.** The `Local recovery storage` text locator matched two elements. The test now requests the exact heading text.
3. **Disposable admin credentials now reach both pytest and Playwright.** Diagnostics forwards the user-supplied test identity without committing credentials into source.
4. **Real scraper URL now has a browser UI journey.** Playwright logs in through the admin UI, opens `Scrape New Series`, fills the supplied URL, clicks **Analyze**, verifies discovered metadata, and removes the disposable draft.
5. **UI access points are inventoried on every run.** The inventory records every current route plus button/link/onClick source access point as evidence beside the runtime report.
6. **Exact 800-case ledger.** `build-user-perspective-report.py` emits `qualification-800.tsv` while retaining the larger runtime result as the authoritative pass/fail gate.

## P12.8.1 no-host-Python harness hotfix

A Windows-machine regression exposed two direct host `python3` invocations in `scripts/run-user-perspective-qualification.sh`, plus three more in the qualification static regression. This violated the existing `hybrid-no-host-python` contract even though the actual API/diagnostics and Playwright acceptance layers were already containerized.

P12.8.1 removes all executable host `python`/`python3` calls from the qualification path:

- `ui-access-point-audit.py` runs through `scripts/hybrid/python-runtime.sh` with `MREADER_PYTHON_FORCE_DOCKER=1`;
- `build-user-perspective-report.py` uses the same forced Docker runtime;
- `user-perspective-qualification-static.sh` is now POSIX-shell-only and checks source shape without launching Python;
- `hybrid-no-host-python.sh` reports zero executable host-Python calls across `scripts/**/*.sh` and `tests/**/*.sh`.

This does not change the runtime acceptance topology. The full API/functional/integration/RBAC/scraper suite still executes in the dedicated `mreader/diagnostics:<version>` container built on `mreader/api-tests:<version>`, and browser E2E still executes in the separate Playwright container. The forced Docker Python helper is only for deterministic source inventory/report assembly on the host orchestration side.
