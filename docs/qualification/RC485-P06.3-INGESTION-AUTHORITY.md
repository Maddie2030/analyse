# RC4.85 P06.3 prerequisite — ingestion publication authority

**Purpose:** supply the durable operation authority that P06.3 needs without prematurely implementing the rest of P07.

## Boundary

Migration `055_ingestion_operation_authority.sql` creates the one approved `ingestion_operations` business-support table. It carries the overall operation identity, source kind, retained requesting actor, parent link, user-visible status/phase, source revision, operation revision, lease/fencing generation, counts, cancellation request, acknowledgement visibility and safe error code.

For a new Catalog publication transaction, `Store.CommitPublication` now:

1. resolves any already-committed idempotency receipt first, so response-loss reconciliation is stable;
2. locks the matching ingestion operation;
3. checks retained actor identity, exact source revision and exact ingestion generation;
4. rejects cancellation and any state other than `running`;
5. rechecks that the retained actor currently exists, is active and has the `admin` role;
6. only then validates Media completion evidence and locks/mutates Catalog targets.

The header intentionally does not hold a foreign key to `users`, so historical operation evidence cannot permanently block account deletion. A cancellation timestamp is also allowed to remain when reconciliation later concludes `completed`, because a commit can win a cancel race.

## Scope boundary with P06.5/P07

This prerequisite does **not** register the private Catalog HTTP route, authenticate workload secrets, or wire all manual/batch/scraper entry points. P06.5 remains responsible for authenticating a narrowly distributed private workload credential before invoking the store; P09.1 is its secret-distribution prerequisite. P07 remains responsible for coordinator creation/update logic, leases, cancellation reconciliation, acknowledgement visibility and cleanup lifecycle.
