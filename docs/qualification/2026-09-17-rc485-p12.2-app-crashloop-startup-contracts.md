# RC4.85 P12.2 — Application crash-loop startup contract repair

Date: 2026-09-17

## Real-host symptom

After the Windows/Docker Desktop hybrid deployment reached Kubernetes, the control plane and most MReader workloads were healthy, but four application workloads entered `CrashLoopBackOff`:

- `mreader-user/auth-service`
- `mreader-admin/auth-admin`
- `mreader-admin/image-service`
- `mreader-user/progress-go`

KEDA, CoreDNS, the Kubernetes control plane, gateways, Catalog, Reader, Realtime, Social, Scraper and frontends were already running, narrowing the failure to application startup contracts rather than cluster health.

## Root causes

### Python SQLAlchemy workloads

Dedicated PostgreSQL role DSNs are intentionally generated in portable `postgresql://...` form. The shared Python database layer passed that URI directly to `sqlalchemy.ext.asyncio.create_async_engine()`. SQLAlchemy therefore selected its synchronous PostgreSQL default driver instead of `asyncpg`, even though Auth and Image images install `asyncpg==0.30.0` and use the async engine API.

`shared/shared/config.py` now normalizes `postgresql://...` and `postgres://...` dedicated workload DSNs to `postgresql+asyncpg://...` at the Python runtime boundary. Go/TypeScript services continue receiving the portable PostgreSQL URI unchanged because the canonical DSN stored in `.env` is not rewritten.

### Progress startup view privilege

`progress-go` calls `ValidateReadingSchema()` before starting HTTP service and selects from canonical view `reading_state_v1`. The `progress_runtime` capability had table access for `chapter_reads`, `reading_progress`, `chapters`, `series` and `users`, but no `SELECT` on `reading_state_v1`. The exact role contract now grants read-only access to that view.

The P09.3 ownership audit was also corrected to distinguish declared PostgreSQL views from tables; it had previously rejected a legitimate view grant because schema discovery tracked tables/functions/sequences only.

## Real-host follow-up: image-service router import cycle

The first repaired package advanced the Python DB-driver and Progress privilege contracts, but the next Windows/Docker Desktop pod run exposed an independent image-service import-time defect before the process could bind port 8000.

Real-host `kubectl logs --previous` showed:

- `app.main` importing `app.routers.jobs` and `app.routers.upload`;
- `jobs.py` importing validation constants from `upload.py`;
- `upload.py` importing `_submit_thumbnail_job` back from the partially initialized `jobs.py`;
- Uvicorn terminating with `ImportError: cannot import name '_submit_thumbnail_job' from partially initialized module 'app.routers.jobs'`.

History inspection showed this entered during the P07.3 staging repair: the compatibility thumbnail route was redirected to the durable job path, but the edit simultaneously removed `IMAGE_MIME_TYPES` from `upload.py` while leaving `jobs.py` importing it there. That meant a second missing-symbol failure existed behind the circular import.

Source `d0558300318c422853c50904b003aaa9067364fe` fixes the dependency direction by moving `SAFE_SLUG`, `THUMBNAIL_NAME`, `IMAGE_MIME_TYPES`, and `ARCHIVE_MIME_TYPES` to neutral `app.media_validation`. Both routers depend on that neutral contract; `jobs.py` no longer imports `upload.py`, while the compatibility upload route can continue delegating to `_submit_thumbnail_job`.
