# RC4.85 P08.8 Write/Cutover Fencing Design

## Goal

Make production PostgreSQL restore a recoverable, installation-bound cutover that cannot reuse stale confirmation, cannot lose its source/safety recovery points during the operation, can recover deterministically from interruption between database renames, and does not replay pre-restore queued/in-flight side effects when the restored database comes live.

P08.8 extends the existing P08.3–P08.7 recovery system. It does **not** introduce another restore queue, another recovery store, another public route, or another restore algorithm.

## Existing boundaries that remain authoritative

- `database_operations` remains the one normal backup/drill/restore queue and status ledger.
- `scripts/backup/backup-agent.sh` remains the one production restore/cutover engine.
- `scripts/backup/local-recovery-store.sh` remains the recovery-bundle verifier and opaque-ID resolver.
- `/api/admin/database` remains the one admin HTTP facade.
- `scripts/backup/postgres-restore.sh` remains the operator CLI and must invoke the same backup-agent restore engine.
- Restore drills remain isolated. They may stage/restore/validate a temporary database and run read-only NAS/media checks, but they may not enter production cutover journaling, advance restore generation, emit production messages, or mutate Media/Catalog production state.
- P07.4 Lifecycle cleanup is generation/path fenced and remains eligible to continue after restore; P08.8 must not blanket-delete or flush that work.

## Chosen architecture

### 1. Host-owned restore control

The backup agent owns one persistent control record under the canonical host-local recovery root:

`$POSTGRES_BACKUP_LOCAL_ROOT/control/restore-control.json`

Schema v1:

```json
{
  "schema_version": 1,
  "installation_id": "<32 lowercase hex, never returned to browser>",
  "installation_fingerprint": "inst_<16 lowercase hex>",
  "restore_generation": 1,
  "updated_at_utc": "2026-09-16T00:00:00Z"
}
```

Rules:

- The canonical recovery root and `control/` must be real directories, never symlinks.
- The installation ID is generated once, written mode `0600`, and never copied from the PostgreSQL database being restored.
- Browser/API surfaces may expose only `installation_fingerprint` and `restore_generation`; the raw installation ID remains host-only.
- Control writes are same-directory temp-file + rename writes, followed by best-effort sync.
- `restore_generation` is monotonic. It advances exactly once for a successfully committed production cutover. Drills never advance it.

This record is the authority when PostgreSQL is offline or has just been replaced.

### 2. PostgreSQL restore-state mirror

Migration `060_database_restore_fencing.sql` adds a singleton `database_restore_state` row containing:

- `installation_fingerprint`
- `restore_generation`
- `last_restore_operation_id`
- `last_restore_source_public_id`
- `updated_at`

The host control remains authoritative. The database row is a runtime mirror for observability and later P09.4 readiness/service-generation enforcement.

The staged candidate receives current migrations before cutover, so this row exists even when restoring an older backup. After the cutover is validated and stale-work reconciliation succeeds, the new live database is updated with the *next* restore generation before the host control commits that generation.

### 3. Exact confirmation binding

The confirmation tuple is:

- opaque recovery public ID (`bkp_<24 hex>`),
- verified source SHA-256,
- installation fingerprint,
- expected restore generation.

The human confirmation text is exactly:

`RESTORE <backup_id> ON <installation_fingerprint> GEN <restore_generation>`

Admin flow:

1. `/api/admin/database` reports the safe `restore_control` fingerprint/generation from the backup-agent heartbeat.
2. The restore modal displays the exact confirmation string.
3. `DatabaseRestoreRequest` carries `backup_id`, `confirmation`, `installation_fingerprint`, and `restore_generation`.
4. The facade re-resolves the selected recovery row, compares the request to the current runtime control tuple, validates the exact confirmation text, and queues the restore with metadata containing `recovery_public_id`, `recovery_sha256`, `expected_installation_fingerprint`, and `expected_restore_generation`.

CLI flow:

1. `postgres-restore.sh` asks the backup agent to resolve `latest`, `latest-snapshot`, or an opaque ID into one verified public ID/source hash plus the current control fingerprint/generation.
2. The CLI uses the same exact confirmation text (unless `--yes` is explicitly supplied).
3. The CLI queues the same restore operation metadata and invokes the same engine.

The backup agent rejects any restore missing this metadata. It re-resolves the public ID and rechecks source SHA/category/recovery ID plus the host fingerprint/generation once when the operation is claimed and again immediately before destructive cutover. A generation/source/installation change invalidates a previously typed confirmation.

### 4. Exact source and safety pins

P08.5 already pins active restore/drill `backup_filename` values and unresolved cutover markers. P08.8 strengthens the cutover journal to contain both:

- `source_recovery_id` / `source_public_id`,
- `safety_recovery_id` / `safety_public_id`.

After the pre-restore safety bundle is created and verified, its exact IDs are read from the existing `latest-pre-restore.json` state and persisted into the cutover journal. Retention pin generation reads both IDs from every active new journal; legacy marker `.filename` remains supported for backward recovery.

Pins remain until the restore is fully reconciled/terminal or an operator resolves an ambiguous journal.

### 5. External cutover phase journal

New journals live outside PostgreSQL under:

`$POSTGRES_BACKUP_LOCAL_ROOT/control/restore-cutover-<operation_uuid>.json`

The agent also continues to recognize legacy `$SPOOL/state/restore-cutover-*.json` markers so earlier RC markers are recoverable.

Schema v2 includes:

- operation ID,
- installation fingerprint,
- expected and next restore generations,
- source public/recovery ID + SHA-256,
- safety public/recovery ID,
- staged/live-old DB names,
- source format,
- audit SQL path,
- `phase`, `created_at_utc`, `updated_at_utc`.

Journal updates are atomic. The agent records phase **before** each destructive transition and again after observing success. Required phases are:

1. `prepared`
2. `rename-live-pending`
3. `live-renamed`
4. `promote-staged-pending`
5. `cutover-live`
6. `reconciling`
7. `generation-commit-pending`
8. `generation-committed`
9. terminal cleanup/removal after the database ledger is safely terminal and the old DB is dropped.

The two database renames are executed as separate steps rather than one heredoc transaction so the journal can distinguish interruption between them.

### 6. Interruption recovery decision rules

On backup-agent startup, journals are reconciled before new destructive operations are accepted.

For a v2 journal:

- If host generation equals `expected_restore_generation`, the cutover has not committed logically. The agent may finalize the candidate only if observed DB names + validation + audit/stale-work reconciliation prove it safe; otherwise it restores the old DB name when that rollback is unambiguous.
- If host generation equals `next_restore_generation`, the cutover decision has committed. The agent validates/finalizes the new live DB and operation ledger; it does not automatically roll back to the old generation.
- Any other installation fingerprint/generation or ambiguous DB-name combination leaves the journal in place and requires operator intervention. The agent does not guess.
- Legacy v1 markers retain the existing reconciliation behavior.

The journal is removed only after terminal reconciliation is proven.

### 7. Selective stale-work reconciliation

Before writes resume on a committed restored database, the backup agent reconciles replay-unsafe durable work in the restored database:

- `ingestion_operations` in active/cancel-pending states become `cancelled`, phase `superseded-by-restore`, with `revision` and `lease_generation` incremented and an explicit restore-superseded error code. This fences old Scraper workers/messages using existing P07 generation checks.
- `media_operations` in `queued`, `retry`, or `processing` become `failed`, their `media_generation` increments, dispatch/heartbeat ownership is cleared, and an explicit restore-superseded error is recorded. This fences old Media workers using the P07 generation contract.
- unpublished `event_outbox` rows are suppressed rather than replayed: set `published_at`, clear locks, record a safe suppression diagnostic, and annotate headers with `restore_suppressed=true` and the new restore generation. The restored business state remains authoritative; pre-restore side effects are not replayed automatically.
- `database_operations` uses the existing audit import and `superseded-by-restore` cancellation logic.
- generation/path-fenced Lifecycle cleanup jobs are **not** blanket-cancelled or flushed.
- shared Redis and unrelated RabbitMQ queues are never globally flushed. Stale messages that arrive after workloads resume meet cancelled/failed/generation-mismatched canonical rows and no-op through existing domain fences.

This is the P08.8 source-level reconciliation boundary. P09.4 later completes deployment-wide readiness/service restore-generation enforcement.

### 8. Generation commit ordering

After database-name cutover:

1. validate the new live DB;
2. import current database-operation audit state;
3. selectively reconcile restored stale work;
4. validate the live DB again;
5. write the new generation/fingerprint into `database_restore_state`;
6. journal `generation-commit-pending`;
7. atomically advance the host control to `next_restore_generation`;
8. journal `generation-committed`;
9. mark the restore operation terminal completed;
10. drop the retained old DB and clean scratch/journal files.

Once the host generation advances, automatic restart recovery finalizes that generation rather than silently reverting it.

### 9. Drill isolation

`restore_drill_selected`, snapshot drill staging, and `postgres-restore-drill.sh` must never:

- create/update production cutover journals,
- create a production pre-restore safety capture,
- call stale-work reconciliation,
- update `database_restore_state`,
- advance host `restore_generation`,
- suppress production outbox rows,
- publish Catalog/Media production work.

Static regression coverage must assert this separation explicitly.

- `db/migrations/060_database_restore_fencing.sql` — database restore-state mirror only.
- `scripts/backup/backup-agent.sh` — host control, exact restore fence validation, source/safety pin journal, phased cutover, restart reconciliation, stale-work reconciliation and generation commit.
- `scripts/backup/postgres-restore.sh` — resolve exact public source/control tuple before prompt; use installation/generation-bound confirmation; invoke the same engine.
- `services/scraper_service/app/database_protection.py` — expose safe restore-control heartbeat fields; queue metadata remains canonical DB operation state.

- `services/scraper_service/app/models.py` — restore request fingerprint/generation fields.
- `frontend/src/api/client.ts` — restore-control response/request types.

- Existing backup/restore runtime/static fixtures are updated only where their contract legitimately changes.

## Failure semantics

Fail closed before destructive cutover when:

- control root/file is missing, malformed, symlinked, or cannot be persisted;
- queued restore metadata lacks exact source/control fields;
- current installation fingerprint/generation differs from the queued expectation;
- the public ID resolves to a different recovery ID/category/SHA-256;
- safety backup cannot be verified/pinned;
- journal cannot be persisted;
- writer quiescence is not established by the operator restore path.

After cutover begins, preserve journal + old database whenever state is ambiguous. Do not remove evidence to make the next startup appear clean.

## Qualification

TDD must prove RED then GREEN for:

- installation-bound/stale-generation admin confirmation;
- CLI binding for `latest`, `latest-snapshot`, and opaque IDs;
- agent-side source SHA/fingerprint/generation recheck;
- exact source+safety retention pins;
- phase journal writes around each rename;
- deterministic recovery for: before first rename, between renames, after second rename before reconciliation, and after generation commit before ledger cleanup;
- ingestion/media generation invalidation and outbox suppression;
- Lifecycle jobs intentionally preserved;
- restore drill cannot touch production control/journal/generation/reconciliation paths.

Then rerun the dependency-light regression suite, recovery/database shell contracts, runnable Scraper suite, API ownership/route/WebP audits, syntax/compile/diff checks, and Ripwire quality. Real Docker/PostgreSQL interruption rehearsal remains a runtime qualification requirement and must be reported blocked if Docker remains unavailable.

## Non-goals

- No new recovery store, admin route namespace, queue, or restore worker.
- No global Redis flush or RabbitMQ purge.
- No P09.3 database-role grant rollout.
- No P09.4 service-wide restore-generation readiness enforcement beyond the P08.8 database mirror and domain generation invalidation described above.
- No P09/P10 work.
