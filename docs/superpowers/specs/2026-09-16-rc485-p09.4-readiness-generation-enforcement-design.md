# RC4.85 P09.4 Readiness and Restore-Generation Enforcement Design

## Status

Approved in chat on 2026-09-16. This design implements only P09.4. P09.3 restrictive grants remain authoritative and must not be broadened. P09.5 route/consumer denial remains out of scope until P09.4 is independently source-qualified and durably checkpointed.

## Goal

Make the supported hybrid deployment and restore/restart path fail closed unless the database schema, P09.3 effective grants, scoped workload credentials, and restore generation all match the exact source tree being deployed. Reuse the existing migration quiescence, P09.3 role reconciliation, P08.8 host restore control, and `database_restore_state` mirror rather than creating a second readiness or recovery authority.

P09.4 closes the integration gap between four already-established contracts:

1. P05 quiescence prevents old writers/autoscalers from racing an in-place migration.
2. P09.3 reconciles exact runtime PostgreSQL privileges and workload-specific DSNs after migrations.
3. P08.8 owns destructive restore generation and mirrors committed generation into PostgreSQL.
4. `scripts/hybrid/deploy.sh` is the normal path that renders workload secrets and resumes application workloads/autoscaling.

The required outcome is one canonical sequence: **quiesce -> migrate -> reconcile grants -> verify readiness/generation -> deploy current workload templates -> prove rollout -> restore autoscaling**.

## Existing authorities this design must preserve

P09.4 is an integration/enforcement layer. It must not replace or duplicate these authorities:

- `scripts/hybrid/quiesce-before-migration.sh` owns pre-migration workload/autoscaler quiescence.
- the current migration runner owns schema migration order and `schema_migrations` state.
- `contracts/ownership/postgres-roles.v1.json` plus the P09.3 role auditor/reconciler own runtime PostgreSQL policy.
- P09.1 workload env-scope files own secret distribution.
- `scripts/backup/backup-agent.sh` owns the host restore control file/journal and committed restore generation.
- `database_restore_state` is a technical PostgreSQL mirror of the host restore generation, not an independent recovery authority.
- `scripts/hybrid/deploy.sh` is the normal current-version application rollout path.
- KEDA/HPA remain the existing autoscaling mechanisms; P09.4 only controls when they regain authority after quiescence/restore.

No new readiness service, database owner registry, restore catalog, generation store, or broad database credential is introduced.

## Architecture decision

Use a **host-side canonical readiness/generation gate** invoked after migrations and P09.3 role reconciliation and before application workloads or autoscalers are resumed.

The gate consumes existing authorities and emits one verified deployment-generation token. That token is non-secret deployment metadata derived from the committed restore generation and the current database/schema/grant contract state. `deploy.sh` stamps it into every database-dependent deployment pod template so a committed restore generation change necessarily causes a Kubernetes rollout of the current source tree.

This is preferred over per-service readiness logic because:

- the checks are installation-wide and depend on host-only/bootstrap authority that application workloads must not receive;
- replica-zero/KEDA workers cannot rely on an HTTP readiness endpoint that is already running;
- implementing the same policy independently in Go, Python and TypeScript would duplicate P09.3/P08.8 authority;
- a host-side gate can prevent workloads from starting at all when the installation state is inconsistent.

It is preferred over a shared init-container/sidecar because that would add another runtime component to every workload and still would not own autoscaler ordering or the host restore-generation authority.

## Canonical readiness inputs

The P09.4 gate reads only existing state:

1. **Expected source schema state**
   - latest migration identity from the checked-in migration set;
   - required owner/schema objects defined by current migrations and the P09.3 contract.
2. **Effective PostgreSQL grant state**
   - P09.3 contract and same-tree auditor output;
   - PostgreSQL catalog verification from the existing reconciler/audit logic.
3. **Scoped workload credential state**
   - all deployed PostgreSQL-using workloads declared in `postgres-roles.v1.json`;
   - each workload's dedicated DSN persisted by the host-side P09.3 reconciliation flow;
   - P09.1 env-scope evidence that only the declared workload receives its DSN.
4. **Restore generation**
   - host `restore-control` generation is authoritative;
   - `database_restore_state` must contain the same committed generation/fingerprint mirror;
   - unresolved/ambiguous P08.8 cutover journals make readiness fail closed.
5. **Deployment topology**
   - current user/admin workload manifests;
   - current HPA/KEDA manifests;
   - current namespace/workload inventory used by hybrid deployment.

The gate must not infer success from configuration files alone when PostgreSQL catalog state can be checked with host authority.

## Canonical deployment sequence

### Normal upgrade/start

The supported current-version path becomes:

1. validate `.env` and host data-path invariants;
2. if upgrading an existing deployment, remove HPA/KEDA authority and quiesce mutation workloads using the existing quiescence path;
3. start/validate stateful dependencies;
4. run current migrations;
5. run P09.3 subtractive role/grant reconciliation;
6. run the P09.4 readiness/generation gate;
7. render workload-specific secrets from the already-verified P09.1/P09.3 source;
8. apply current application deployment manifests with the verified generation token stamped into pod templates;
9. wait for required deployment rollouts to succeed;
10. install/apply HPA/KEDA only after the current workloads are ready;
11. verify KEDA metric connectivity with the dedicated read-only metrics identity.

If any step from migration through rollout fails, autoscaling must remain disabled and the command must exit non-zero. The operator may repair/retry the same sequence; there is no broad-credential fallback.

### Fresh installation

A fresh installation has no old workloads to quiesce. It still must run migrations, P09.3 reconciliation, P09.4 readiness, current workload rollout, then autoscaling in that order.

The absence of an old deployment is not permission to skip the readiness/grant/generation checks.

## Restore and interruption-recovery sequence

P08.8 remains the destructive restore engine. P09.4 changes only how the application plane is resumed after a committed/restored database becomes authoritative.

After P08.8 has validated the restored database, reconciled replay-unsafe application work, and committed the next host restore generation:

1. application writers remain quiesced and autoscalers remain without authority;
2. current migrations are applied to the restored database when required by the existing restore path;
3. P09.3 role reconciliation runs against the restored current schema;
4. P09.4 verifies host generation == `database_restore_state` generation, exact schema, exact effective grants, required scoped DSNs, and absence of ambiguous restore journals;
5. the current deployment path is invoked with the verified generation token;
6. current user/admin workloads roll to templates containing that token;
7. only after required rollout success are HPA/KEDA restored.

An interrupted restore recovered by the P08.8 journal must converge through the same steps before application writers resume. There is no direct restore-only `kubectl apply` path that bypasses current migrations/grants/readiness.

## Restore-generation authority and mirror rules

The host restore control remains primary.

`database_restore_state` is accepted only as a mirror when all of the following hold:

- its row/shape matches the current migration contract;
- its installation fingerprint matches the host restore control;
- its committed generation equals the host committed generation;
- no unresolved v2 restore-cutover journal indicates an earlier/later ambiguous phase.

A missing row, duplicate/invalid row, installation mismatch, generation mismatch, or ambiguous recovery journal is a readiness failure.

P09.4 must not repair a mismatch by silently choosing the larger generation. Repair remains a recovery/operator concern under P08.8. The readiness path observes and blocks; it does not invent recovery truth.

## Verified deployment generation token

P09.4 produces a deterministic non-secret token only after the readiness gate passes.

The token must bind at least:

- committed restore generation;
- installation fingerprint or a non-secret digest of it suitable for template metadata;
- current latest migration identity;
- current P09.3 role-contract version/hash.

The raw database password/DSN, backup IDs and recovery source hashes must not appear in the token or pod metadata.

The token is stamped into every database-dependent deployment template through an annotation and/or environment value such as `MREADER_DEPLOYMENT_GENERATION`. The exact key may differ, but there must be one canonical implementation and one deterministic value per verified installation state.

A change in restore generation or grant/schema contract must change the pod template and force a rollout. Re-running deployment without a state change must be idempotent and must not churn pods solely because of timestamps/random values.

## Workloads covered by generation stamping

At minimum, every PostgreSQL-using workload declared by the P09.3 contract is generation-bound, including replica-zero workers. This includes the current applicable set such as:

- Auth user/admin;
- Catalog user/admin;
- Reader;
- Progress;
- Social;
- Scraper API/batch/series workers;
- Image/Media workers that use PostgreSQL;
- Notification Worker;
- Outbox Relay;
- Lifecycle Worker;
- Realtime;
- any other workload present in the same-tree P09.3 contract.

A workload proven by the P09.3 contract to have no PostgreSQL dependency does not need database-generation gating merely because it is nearby in the deployment manifest. Gateway/frontend components may still roll as part of a normal current-version deploy, but they are not granted database authority.

Replica-zero/KEDA workloads are specifically covered: their Deployment template must carry the verified generation before KEDA is re-enabled so a later scale-up cannot resurrect an old pre-restore template.

## Schema/readiness checks

The gate must fail when the current source tree and live database disagree on required schema state.

Checks include:

- latest checked-in migration is recorded in `schema_migrations`;
- required P09.3 tables/views/functions/sequences referenced by the contract exist with expected object kinds;
- required owner/schema objects used by current stores are present;
- no pending migration needed by the current tree is skipped;
- P09.3 effective privilege verification succeeds after reconciliation.

P09.4 does not duplicate every service-specific schema validation. Existing service readiness checks such as Progress `ValidateReadingSchema` remain useful second-line checks. P09.4 is the installation-wide pre-rollout gate.

## Grant/readiness checks

The gate must call/reuse the P09.3 same-tree role audit and effective PostgreSQL catalog verifier rather than implementing a second privilege model.

It must prove before rollout:

- every required capability/workload role exists with P09.3 security attributes;
- expected memberships and table/view/sequence/function privileges are effective;
- revoked/forbidden broad privileges remain absent;
- PUBLIC/default-function fail-closed rules remain effective;
- no application workload is configured to receive the bootstrap migration/protection credential;
- KEDA continues to use only its dedicated read-only metrics DSN.

A role reconciliation failure or post-reconcile verification failure blocks deployment.

## Scoped credential readiness

For every PostgreSQL-using workload being deployed:

1. its P09.3 contract row declares one dedicated DSN key;
2. the protected host source contains a valid role-specific DSN for that workload role;
3. the workload P09.1 scope declares only the runtime key that process expects;
4. generated Kubernetes secret data receives the dedicated DSN;
5. the workload does not reconstruct/fall back to bootstrap `POSTGRES_USER`, `POSTGRES_PASSWORD` or a broad generic `DATABASE_URL`.

P09.4 validates readiness of this distribution before rollout; it does not broaden P09.1 scope lists.

Missing or malformed narrow credentials fail deployment with an actionable workload/key error.

## Quiescence and autoscaler ownership

P09.4 preserves the existing P05 ordering rule: autoscalers lose authority before replica counts are changed.

The canonical rules are:

- delete/disable current HPA and KEDA ScaledObjects before migration/restore quiescence;
- wait for targeted mutation deployments to reach zero as required by the existing quiescence contract;
- preserve the special legacy Progress drain semantics already implemented by the P05 migration path;
- do not reinstall autoscalers until current workloads have rolled out successfully on the verified generation;
- if rollout/readiness fails, leave autoscalers disabled rather than allowing them to recreate stale writers.

P09.4 must not invent a second list of mutation workloads when the existing quiescence/topology manifests can be used. Any necessary inventory helper must derive from those current manifests/contracts.

## Deployment manifest strategy

Do not hand-edit a generation value into every YAML file.

Preferred implementation:

1. keep checked-in manifests generation-neutral;
2. after P09.4 verification, render/patch database-dependent Deployment templates in the deploy pipeline with the deterministic verified generation token;
3. apply the patched manifests;
4. verify that the live Deployment template contains the token before declaring rollout successful.

The implementation may use `kubectl set env`, a deterministic `kubectl patch`, or a temporary rendered manifest. The choice must preserve reproducibility and must not persist secrets in generated artifacts.

P09.4 must not add Helm/Kustomize solely for this feature.

## Failure semantics

P09.4 uses fail-closed categories, each with a distinct actionable error:

- `schema-not-ready`: migration/schema contract mismatch;
- `grants-not-ready`: P09.3 audit/reconcile/catalog verification mismatch;
- `credentials-not-ready`: missing/invalid narrow DSN or scope mismatch;
- `generation-not-ready`: host/DB generation or installation mismatch;
- `restore-state-ambiguous`: unresolved P08.8 journal/cutover state;
- `rollout-failed`: current workload deployment did not become ready;
- `autoscaling-not-restored`: workload rollout succeeded but autoscaler restore/check failed.

The exact machine-readable representation may be shell exit codes/messages rather than a new persisted status model. P09.4 does not add a second operations queue.

A failure before application rollout leaves existing quiesced replicas/autoscalers unchanged. A failure during rollout does not re-enable autoscaling. Recovery is to repair the underlying condition and rerun the canonical deploy sequence.

## Relationship to service readiness endpoints

P09.4 does not require every service to receive host restore-generation authority or query `database_restore_state`.

Existing service-local readiness checks continue to verify local dependencies/schema assumptions. Services that already fail closed when their required schema is absent should keep doing so.

The installation-wide P09.4 gate prevents known-invalid state from being rolled out in the first place. This avoids granting all services direct read access to technical restore state solely for readiness.

A service may receive the non-secret deployment-generation token for observability, but it does not become an authority on restore generation.

## Static and dependency-light verification

P09.4 adds source-level regression coverage that proves the orchestration contract without requiring Docker/PostgreSQL/Kubernetes to be available.

Required RED/GREEN cases include:

1. deploy ordering is migrate -> reconcile grants -> P09.4 gate -> workload rollout -> autoscaling;
2. missing latest migration/schema object blocks readiness;
3. P09.3 effective-grant verification failure blocks readiness;
4. missing required role-specific DSN blocks before secret/apply rollout;
5. bootstrap credential fallback is absent;
6. host/DB restore-generation mismatch blocks rollout;
7. installation-fingerprint mismatch blocks rollout;
8. unresolved P08.8 restore journal blocks rollout;
9. failed readiness cannot reinstall HPA/KEDA;
10. failed workload rollout cannot reinstall HPA/KEDA;
11. generation advancement changes the database-dependent Deployment pod template;
12. unchanged verified state yields a stable/idempotent generation token;
13. replica-zero/KEDA workers carry the current generation template before KEDA is enabled;
14. restore/restart path calls the canonical reconciliation/readiness/deploy sequence rather than directly reviving workloads;
15. KEDA continues to use its P09.3 read-only metrics identity;
16. P09.5 route/consumer denial is absent from the P09.4 diff.

Existing P05 migration quiescence, P08.8 restore fencing and P09.3 grant tests remain mandatory regressions.

## Runtime qualification

A real P09.4 runtime gate requires an authorized Docker Desktop/Kubernetes + disposable/current PostgreSQL environment because it must observe actual quiescence, PostgreSQL catalogs, deployment templates, rollout and KEDA/HPA behavior.

The runtime gate should prove at least:

1. start a current deployment on generation N;
2. quiesce/remove autoscaler authority;
3. apply current migrations and P09.3 reconciliation;
4. verify P09.4 readiness passes and workloads roll with token for N;
5. simulate/perform an authorized restore-generation advance to N+1 through P08.8-compatible state;
6. prove generation mismatch blocks rollout before mirror reconciliation;
7. reconcile/commit the mirror, then prove current workloads roll with N+1 token;
8. prove a replica-zero worker later scaled by KEDA starts from the N+1 template;
9. prove HPA/KEDA are not restored on any failed readiness/rollout path;
10. verify application workloads still cannot use broad bootstrap credentials.

When Docker/Kubernetes/PostgreSQL are unavailable, this runtime gate is **blocked**, not passed. P09.4 may be source-qualified with the blocker recorded, but runtime qualification remains open for P11/authorized runtime execution.

The blocked P09.3 real PostgreSQL permission gate remains a separate blocker; P09.4 source work must not relabel it as passed.

## Expected implementation surface

The design should primarily evolve existing orchestration code rather than application business logic. Expected files include:

- a small host-side P09.4 readiness/generation verifier under `scripts/hybrid/` or `scripts/tests/` with reusable validation logic;
- `scripts/hybrid/stateful-up.sh` or the current migration/reconcile caller, to expose the verified post-migration state cleanly;
- `scripts/hybrid/deploy.sh`, to enforce the gate, stamp current generation, order rollout before autoscaling, and verify template state;
- `scripts/hybrid/quiesce-before-migration.sh` only if a minimal reusable autoscaler/quiescence helper is required;
- `scripts/backup/backup-agent.sh` only where the restore-resume path must call the canonical current deployment/reconcile gate rather than directly reviving workloads;
- deployment manifests only if metadata hooks are needed; avoid repetitive hand-stamped values;
- P09.4-focused regression tests plus updates to existing migration/restore/deployment contract tests;
- operator documentation describing the fail-closed sequence and blocked-runtime distinction.

Application domain services should not be modified merely to mirror host-level generation state unless exact same-tree evidence proves a service-local readiness gap cannot be enforced centrally.

## Compatibility and migration strategy

1. Add the P09.4 static readiness/generation contract and tests without changing running deployments.
2. Implement the host verifier using existing P09.3/P08.8 authorities.
3. Integrate it into normal deploy ordering before application `kubectl apply`/rollout.
4. Add deterministic generation stamping to database-dependent Deployment templates.
5. Move HPA/KEDA application after successful workload rollout where current ordering allows them earlier.
6. Route restore/restart resumption through the same current deploy gate.
7. Run full dependency-light, P05, P08.8 and P09.3 regressions plus Ripwire/ownership audits.
8. Execute the runtime gate only on an authorized Docker/Kubernetes/PostgreSQL environment; otherwise record it blocked.

No existing data is reset. No migration identity is rewritten. No NAS media object is modified by P09.4.

## Non-goals

P09.4 does not:

- implement P09.5 route/consumer denial;
- redesign domain ownership or the P09.3 role matrix;
- create a database-per-service model;
- grant applications access to bootstrap migration/protection credentials;
- make `database_restore_state` a second recovery authority;
- replace P08.8 cutover journaling or operation fencing;
- replace service-local health/readiness endpoints;
- add Helm/Kustomize or a new deployment platform;
- change resource limits to make a gate pass;
- claim Docker/PostgreSQL/Kubernetes runtime acceptance from source/static tests.

## Acceptance boundary

P09.4 can be called **source-qualified** only when:

- the canonical deploy path fails closed on missing schema/grants/narrow credentials/generation agreement;
- normal upgrade and restore/restart share the same post-migration reconcile/readiness/deploy sequence;
- database-dependent workloads are deterministically stamped with the verified generation;
- replica-zero workers cannot retain a pre-restore template;
- HPA/KEDA regain authority only after current workload rollout succeeds;
- P09.1/P09.3 narrow credential boundaries remain intact;
- P05 quiescence and P08.8 restore fencing remain intact;
- full relevant dependency-light/ownership/route/security regressions and Ripwire quality checks pass;
- every unavailable real runtime gate is explicitly recorded as blocked, not passed.

P09.4 is **runtime-qualified** only after the real hybrid/PostgreSQL generation/readiness gate executes successfully in an authorized environment.

P09.5 remains unopened until P09.4 source qualification and the standing source+tracker+Library durability checkpoint are complete.
