# RC4.85 P09.2 Ownership / Route Manifest Design

## Status

Approved in chat on 2026-09-16. This design defines P09.2 only. P09.3 restrictive database grants, P09.4 readiness/generation enforcement, and P09.5 route/consumer enforcement are downstream consumers and are explicitly out of implementation scope here.

## Goal

Create one machine-readable, versioned ownership contract for every current in-scope MReader HTTP operation so later security/readiness work can reason from declared route ownership instead of scattered source assumptions. The contract must be exact against the current sequential source, gateway exposure, authentication boundary, mutation authority, downstream dependencies, consumers, events, and executable acceptance evidence.

## Existing authorities to preserve

P09.2 must compose with, not replace, these existing authorities:

- `scripts/tests/api-route-audit.py` — source route discovery plus exact comparison against `tests/api/endpoint_coverage.tsv`.
- `tests/api/endpoint_coverage.tsv` — executable route coverage/evidence inventory for the current 136 source routes.
- `deploy/docker-desktop-hybrid/Caddyfile.user` — public/user plane exposure and public-side denials.
- `deploy/docker-desktop-hybrid/Caddyfile.admin` — admin plane exposure and write routing.
- `tests/regression/api-flow-ownership-static.sh` — selected high-value ownership invariants already proven in source.
- P06/P07/P08 ownership, publication, lifecycle, restore and generation boundaries already source-qualified on the current sequential branch.
- P09.1 scoped-secret selection at `0f1fadb`; P09.2 must not broaden credentials or secret distribution.

`reference/p09.2-manifest-wip` is evidence only. Its `tests/regression/test_ownership_route_manifest.py` contains useful invariants (versioned contract, unique operation IDs, exact current-route coverage, mutating-route authority, admin-plane protection) but its old field names, old route assumptions and blanket planned-route requirement are not authoritative.

## Design choice

Use a **hybrid authoritative manifest + source auditor**.

A fully handwritten manifest would drift because route existence, handler movement and gateway exposure change with source. A fully generated manifest would be incomplete because static analysis cannot reliably infer business ownership, permitted writes, event effects, intended consumers or semantic dependencies. P09.2 therefore separates:

1. **Explicit semantic declarations** — ownership, write authority, dependencies, consumers, events and acceptance gates.
2. **Derived source facts** — current route set, exact handler declaration, route method/path, gateway exposure and coverage evidence.
3. **Cross-validation** — the auditor fails if explicit declarations disagree with facts derivable from current source.

The manifest is authoritative for semantics only after the auditor proves it still matches source.

## Artifacts

P09.2 creates these canonical artifacts:

- `contracts/ownership/routes.v1.json` — the current version-1 ownership manifest.
- `contracts/ownership/routes.schema.v1.json` — JSON Schema for structure and allowed descriptor shapes.
- `contracts/ownership/README.md` — field semantics, identifier conventions, maintenance workflow and downstream-consumer rules.
- `scripts/tests/ownership-route-audit.py` — P09.2 semantic/source/gateway/auth/evidence validator.
- `scripts/run-ownership-route-audit.sh` — stable shell entrypoint for local/CI use.
- `tests/regression/test_p09_2_ownership_route_manifest.py` — regression contract for schema and cross-source invariants.

The existing `scripts/tests/api-route-audit.py` remains the route coverage authority. P09.2 may import/reuse its route-discovery helpers, but must not fork a second incompatible route parser.

## Top-level manifest contract

The JSON document has this shape:

```json
{
  "contract": "mreader.ownership-routes",
  "version": 1,
  "generated_from": {
    "route_coverage": "tests/api/endpoint_coverage.tsv",
    "user_gateway": "deploy/docker-desktop-hybrid/Caddyfile.user",
    "admin_gateway": "deploy/docker-desktop-hybrid/Caddyfile.admin"
  },
  "routes": []
}
```

`generated_from` is provenance, not a substitute for validation. The auditor reads the live files named there and rejects stale or missing inputs.

## Route row

Each current route row contains exactly the following semantic groups.

### Identity and lifecycle

```json
{
  "operation": "catalog.series.list",
  "method": "GET",
  "path": "/api/catalog/series",
  "lifecycle": "current",
  "access_plane": "both",
  "owner": "catalog",
  "handler": "services/catalog_go/internal/httpapi/api.go:listSeries",
  "version": "v1"
}
```

Rules:

- `operation` is a stable lower-case identifier matching `^[a-z][a-z0-9_.-]+$` and unique across the file.
- `(method, path, lifecycle)` is unique.
- P09.2 contains **current source operations only**. Planned operations are excluded until a real source route exists. This intentionally differs from the historical WIP branch.
- `access_plane` is one of `public`, `admin`, `both`, `internal`.
- `owner` is a normalized service/domain identifier such as `catalog`, `auth`, `reader`, `progress`, `social`, `realtime`, `media`, `scraper`, `database-protection`.
- `handler` is an exact repo-relative source path plus callable/symbol name and must exist in the live tree.
- `version` is the semantic route-contract version exposed by that operation (`v1` for current unversioned HTTP contracts unless a stronger route-specific version already exists).

### Authentication

Authentication is structured so later route/readiness tooling does not parse prose:

```json
"authentication": {
  "mode": "session",
  "principal": "user",
  "required_role": null,
  "credential_scope": null
}
```

Allowed `mode` values:

- `none`
- `session`
- `admin-session`
- `workload-token`
- `chapter-grant`
- `mixed`

Fields:

- `principal`: `anonymous`, `user`, `admin`, `workload`, `chapter-reader`, or `mixed`.
- `required_role`: explicit application role when enforced, otherwise `null`.
- `credential_scope`: workload-token/secret scope identifier when relevant, otherwise `null`.

The auditor validates the parts that are statically provable: admin dependency usage, workload-token/internal route helpers, chapter-grant/token helpers, and gateway plane. It must fail closed on obvious contradictions (for example, an `/internal/v1/...` workload route declared as browser session/public).

### Permitted writes

`permitted_writes` is always an array. Read-only routes use `[]`.

Each descriptor has a normalized `kind` and kind-specific fields:

PostgreSQL example:

```json
{
  "kind": "postgres",
  "resource": "series",
  "actions": ["insert", "update"]
}
```

RabbitMQ/outbox example:

```json
{
  "kind": "event",
  "resource": "chapter.published",
  "actions": ["publish"]
}
```

SeaweedFS example:

```json
{
  "kind": "seaweedfs",
  "resource": "chapter-pages",
  "actions": ["create"]
}
```

Redis/Valkey example:

```json
{
  "kind": "cache",
  "resource": "reader-chapter-grants",
  "actions": ["write"]
}
```

Allowed `kind` values for P09.2 are `postgres`, `event`, `seaweedfs`, `cache`, `filesystem`, and `external-http`.

The manifest declares **permission/ownership**, not an exhaustive SQL trace. `resource` uses stable domain/table/topic names. P09.3 will consume only `kind=postgres` rows; therefore PostgreSQL resources must use exact table names where the route directly owns table mutation. Event resources use exact topic/event names where current code establishes them.

All current POST/PUT/PATCH/DELETE operations must either:

- declare at least one permitted write, or
- be explicitly allowlisted by the schema/auditor as command-shaped but externally side-effect-free (for example a validation-only endpoint). Such exceptions must carry acceptance evidence and cannot be inferred silently.

### Dependencies

Dependencies are normalized objects rather than prose:

```json
"dependencies": [
  {"kind": "service", "name": "catalog"},
  {"kind": "postgres", "name": "primary"},
  {"kind": "event-bus", "name": "rabbitmq"}
]
```

Allowed kinds: `service`, `postgres`, `cache`, `event-bus`, `seaweedfs`, `filesystem`, `external-http`.

Dependencies describe resources the handler must call/read/write synchronously or durably enqueue through. They do not attempt to list every transitive library.

### Consumers

Consumers are explicit intended callers:

```json
"consumers": [
  {"kind": "web", "name": "frontend"},
  {"kind": "android", "name": "mreader-android"}
]
```

Allowed kinds: `web`, `android`, `admin-web`, `service`, `operator`.

For `internal` routes, browser consumers are forbidden. For public/admin routes, empty consumers are allowed only when the route is infrastructure/health or when executable evidence proves it is intentionally unused by a first-party client.

The auditor validates first-party consumers when a literal/current source reference is available. It does not pretend dynamic or external consumers can always be discovered statically.

### Events

Events are explicit effects/inputs of the operation:

```json
"events": [
  {"direction": "publish", "name": "chapter.published"}
]
```

Allowed directions: `publish`, `consume`, `request`.

P09.2 records only events proven by current source or an existing ownership contract. It must not recreate retired duplicate publishers removed during P06/P07.

### Acceptance evidence

```json
"acceptance_test_ids": ["API-01", "OWN-01"],
"evidence": [
  "tests/api/test_04_catalog.py",
  "tests/regression/api-flow-ownership-static.sh"
]
```

- `acceptance_test_ids` uses existing canonical gate IDs and format `^[A-Z]+-[0-9]{2}$`.
- `evidence` paths must exist.
- Every current route must include the route-specific evidence already present in `tests/api/endpoint_coverage.tsv`; additional ownership/security evidence can be added.
- The P09.2 auditor does not replace the endpoint coverage audit; it cross-links to it.

## Gateway model

The auditor derives effective browser access from both Caddy files.

Required invariants:

- User gateway `/internal` remains denied.
- User gateway admin APIs remain denied.
- User gateway Catalog POST/PUT/PATCH/DELETE remains denied.
- Admin gateway may expose admin/write namespaces already routed there.
- Routes explicitly routed on both planes must declare `both`.
- Routes reachable only through the user gateway declare `public`.
- Routes reachable only through the admin gateway declare `admin`.
- Catalog `/internal/v1/...` workload routes are `internal` regardless of service-local registration because both browser gateways deny `/internal`.
- The host-local recovery bridge is not represented as a browser route because it is not part of the in-scope source HTTP route set exposed through the MReader gateways.

Gateway parsing should be conservative and specific to the current Caddy matcher patterns. P09.2 must not introduce a general Caddy parser.

## Source route and handler derivation

`source_routes()` from `scripts/tests/api-route-audit.py` remains the canonical route scanner. P09.2 extends the reusable discovery layer to also return source provenance:

```python
RouteSource(
    method: str,
    path: str,
    file: str,
    symbol: str,
)
```

The current 136-route set is the initial required cardinality. The implementation must never hard-code `136`; exact-set comparison makes the test naturally follow legitimate future route additions/removals.

When multiple decorators register the same normalized route key, discovery must fail as ambiguous rather than silently choose one handler.

## Validation layers

The P09.2 audit runs these layers independently and reports all detected errors in one run.

### 1. Schema and identifier validation

Validate JSON against `routes.schema.v1.json`, then enforce uniqueness, normalized identifier formats, lifecycle/access-plane enums and descriptor enums.

### 2. Exact current-route coverage

Compare:

- live `source_routes()` keys,
- `tests/api/endpoint_coverage.tsv` keys,
- current `routes.v1.json` keys.

All three sets must match exactly. No planned-only route is allowed in v1.

### 3. Handler provenance

Every manifest handler must equal the live route declaration provenance returned by the source scanner. File existence alone is insufficient.

### 4. Gateway exposure

Derive route plane from current user/admin Caddy policies and compare to manifest `access_plane`. Fail obvious contradictions or gateway leaks.

### 5. Authentication consistency

Use source-pattern validators for current framework idioms:

- FastAPI dependencies such as `Depends(require_admin)`.
- session/user dependencies and helpers.
- internal/workload token checks.
- reader chapter-grant/token checks.
- Go/TypeScript auth/session middleware patterns already present in the repo.

The validator is intentionally conservative. Unknown auth shapes fail with a message requiring either supported source mapping or an explicit test-backed exception in the audit code, not a manifest self-exemption field.

### 6. Mutation authority

For current POST/PUT/PATCH/DELETE routes require explicit permitted writes and validate high-value ownership against existing static contracts. The auditor also rejects known forbidden duplicate authority patterns already encoded by `api-flow-ownership-static.sh`.

P09.2 does not attempt perfect SQL data-flow analysis. The manifest remains the semantic declaration, while selected source assertions prove the important ownership boundaries.

### 7. Consumers, dependencies and events

Validate identifiers and source/evidence references. Where first-party source contains literal API/event references, check that declared consumers/events do not contradict them. Unknown dynamic relationships are allowed only when backed by an existing evidence file.

### 8. Acceptance evidence

Ensure each acceptance gate ID is well formed and each evidence path exists. Ensure the endpoint coverage evidence row for the same `(method,path)` appears in the manifest evidence set.

## Relationship to later P09 lanes

P09.2 produces data; it does not enforce runtime permissions.

- **P09.3** reads `permitted_writes[kind=postgres]` and service ownership to construct/reconcile least-privilege database grants.
- **P09.4** may use owner/dependency data when enforcing readiness and restore-generation compatibility.
- **P09.5** consumes `access_plane`, authentication, consumers and event declarations for deny tests and route/event contract enforcement.

These consumers must treat `routes.v1.json` as valid only when the P09.2 audit passes against the same source revision.

## Migration / rollout

P09.2 is source-only metadata/tooling and requires no database migration or runtime deployment change.

Implementation sequence:

1. Extend current route discovery to expose exact handler provenance without changing existing route-audit behavior.
2. Add schema + RED ownership-manifest tests using the historical WIP only as fixture inspiration.
3. Populate the current manifest from the 136 live routes and coverage evidence, then curate semantic fields from current source/ownership contracts.
4. Add gateway/auth/write/consumer/event consistency checks.
5. Add a stable runner and include it in the existing regression/route validation flow.
6. Run full route, ownership and dependency-light regression qualification.

## Failure handling

The ownership audit is fail-closed:

- missing route declaration -> failure;
- stale route declaration -> failure;
- handler mismatch -> failure;
- duplicate operation/route key -> failure;
- gateway plane contradiction -> failure;
- mutating operation with undeclared write authority -> failure;
- internal route with browser consumer -> failure;
- missing coverage evidence -> failure;
- unknown descriptor enum or malformed identifier -> failure.

It should aggregate errors and print route identifiers so a developer can repair multiple manifest rows in one iteration.

## Testing strategy

P09.2 qualification must include:

- RED -> GREEN schema/manifest unit tests.
- exact three-way route-set comparison against live source and `endpoint_coverage.tsv`.
- handler provenance tests.
- user/admin/internal gateway-plane tests.
- auth contradiction tests.
- mutating-route write-authority tests.
- internal-route browser-consumer denial tests.
- acceptance evidence existence/cross-link tests.
- existing `api-route-coverage-static.sh` and `api-flow-ownership-static.sh` unchanged and green.
- full dependency-light regression suite and runnable Scraper suite.
- Ripwire quality delta at `gating=0` before source checkpoint.

## Non-goals

P09.2 does not:

- change database grants or credentials;
- expose or retire HTTP routes;
- change Caddy routing;
- alter authentication behavior;
- add runtime readiness/generation checks;
- change publication/lifecycle/recovery ownership;
- create planned/future route declarations with no source route;
- infer all transitive dependencies or external consumers automatically;
- start P09.3, P09.4 or P09.5 implementation.

## Acceptance criteria

P09.2 is source-qualified when:

1. `routes.v1.json` exists, validates against `routes.schema.v1.json`, and declares every live in-scope route exactly once.
2. Live source, endpoint coverage TSV and manifest route sets are exactly equal.
3. Every route has a unique stable operation ID, exact current handler, owner, access plane, authentication object, permitted-writes list, dependencies, consumers, events, acceptance gate IDs and executable evidence.
4. Gateway-derived plane and manifest plane agree for all routes, including admin denials and internal workload routes.
5. All current mutations have explicit write authority or a narrowly coded/test-backed side-effect-free exception.
6. Internal/workload routes cannot declare browser consumers or browser authentication.
7. Existing route/ownership audits remain green; the new ownership audit is integrated as an additional gate rather than a replacement.
8. Full source qualification passes with no Ripwire gating regressions.
9. P09.3/P09.4/P09.5 source remains untouched.
