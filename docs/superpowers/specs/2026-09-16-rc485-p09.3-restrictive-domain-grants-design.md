# RC4.85 P09.3 Restrictive Domain Grants Design

## Status

Approved in chat on 2026-09-16. This design implements only P09.3. P09.4 readiness/generation enforcement and P09.5 route/consumer denial remain out of scope.

## Goal

Replace broad application PostgreSQL credentials with explicit, non-superuser runtime identities whose privileges match the audited P09.2 ownership manifest plus a documented set of non-route worker/technical exceptions. Preserve one migration/protection authority for host-side schema and recovery work, and expose each runtime database credential only to the workload that needs it through the existing P09.1 scoped-secret mechanism.

## Existing authorities this design must preserve

P09.3 does not invent ownership. It consumes existing authorities:

1. `contracts/ownership/routes.v1.json` is the request-route write contract only when `./scripts/run-ownership-route-audit.sh` passes on the same tree.
2. `docs/superpowers/specs/2026-09-15-mreader-rc485-ownership-consolidation-reference.md` section 9.3 is the existing table disposition/owner reference.
3. P09.1 workload env scopes under `deploy/docker-desktop-hybrid/env-scopes/*.keys` are the secret-distribution boundary. A secret present in `.env` is not visible to a workload unless its scope file opts in.
4. The current migration/backup/protection path remains the schema/recovery authority. Application roles do not gain migration, role-management, database-management, replication, or recovery privileges.

P09.3 must not weaken any of these authorities or add a second ownership registry.

## Architecture decision

Use two PostgreSQL role layers:

- **Capability roles (`NOLOGIN`)** encode reusable database privileges for a domain or technical responsibility.
- **Workload login roles (`LOGIN`)** are the identities actually used by services and workers. Each login role is a member of only the capability roles required by that workload.

Direct grants to every workload login are rejected because they duplicate policy and drift. Security-definer functions for every mutation are rejected for P09.3 because that would redesign existing repositories/ORMs instead of enforcing the current architecture.

## Runtime role security baseline

Every runtime login and capability role must be created/reconciled as:

- `NOSUPERUSER`
- `NOCREATEDB`
- `NOCREATEROLE`
- `NOREPLICATION`
- `NOBYPASSRLS`

Runtime logins receive database `CONNECT` and schema `USAGE` only where required. They do not own the database, schema, tables, sequences, or migrations. They cannot change grants or create roles/databases.

`PUBLIC` must not retain broad table/sequence/function privileges that defeat the explicit role model. Grant reconciliation therefore revokes broad inherited/default access before applying the contract.

## Bootstrap and protection authority

The existing host/bootstrap PostgreSQL credential remains available only to:

- database initialization and migrations,
- grant/role reconciliation,
- database-protection backup/restore/drill paths,
- host-side diagnostics that explicitly require migration/protection authority.

Kubernetes application workloads must not receive this broad username/password after P09.3. The role-reconciliation process may use it to create/alter runtime roles and apply grants.

The broad credential must not be reintroduced as a fallback when a workload-specific DSN is missing. Missing or invalid runtime credentials make the affected workload/deployment unready/fail deployment rather than silently widening privileges.

## Contract artifacts

P09.3 adds one versioned database-access contract beside the P09.2 ownership manifest:

- `contracts/ownership/postgres-roles.v1.json`
- `contracts/ownership/postgres-roles.v1.schema.json`
- `contracts/ownership/POSTGRES-ROLES.md`

This contract does not replace P09.2. It maps route ownership plus worker/technical exceptions into database privileges.

The contract contains:

- `contract`, `version`, and source authority references;
- capability-role definitions;
- workload-login definitions and capability memberships;
- explicit table/view/sequence/function grants;
- explicit worker/technical write exceptions;
- expected secret/DSN env key for each workload;
- acceptance-test IDs and evidence paths.

Unknown fields are rejected. Duplicate role names, duplicate workload identities, undeclared tables/functions, and unsupported privilege verbs fail the audit.

## Capability role model

The exact SQL role names may be prefixed for installation safety, but their semantic identities are stable.

### Domain capabilities

| Capability | Primary responsibility |
| --- | --- |
| `auth_runtime` | Auth-owned user/account/session data and declared account-deletion effects |
| `catalog_runtime` | Catalog-owned series/chapter/page/taxonomy/curation/publication receipts and declared lifecycle/outbox enqueue paths |
| `progress_runtime` | Progress-owned reading state, chapter-read facts, and reading view access |
| `social_runtime` | Social-owned bookmarks/subscriptions/ratings/comments plus the declared notification read-state/retention exception |
| `reader_runtime` | Reader-owned derived reading/trending analytics writes and required Catalog/Progress reads |
| `scraper_runtime` | Scraper-owned draft/batch/staging/ingestion operation detail plus declared Catalog/lifecycle/outbox integration writes |
| `media_runtime` | Media/Image API operation/task detail and declared media-generation outputs/state |
| `database_protection_api_runtime` | Narrow admin-facade access to queue/cancel `database_operations` and read the recovery projection; this is not host migration/restore authority |

### Technical/worker capabilities

| Capability | Primary responsibility |
| --- | --- |
| `notification_worker_runtime` | Create notification rows and maintain notification dedupe receipts; not notification read-state ownership |
| `outbox_relay_runtime` | Claim/update event delivery state only; no producer INSERT authority |
| `lifecycle_worker_runtime` | Execute/update durable lifecycle cleanup jobs; producer enqueue remains with authorized domain writers |
| `realtime_runtime` | Read-only runtime data required for realtime fan-out/reconciliation |
| `keda_metrics_runtime` | Read-only queue/status metrics used by KEDA PostgreSQL scalers |
| `image_runtime` | Only database access actually required by image-service paths; otherwise no DB credential |
| `catalog_admin_runtime` | Same Catalog database authority as Catalog where the admin binary is the same owner, not a broader admin database role |
| `auth_admin_runtime` | Same Auth authority as Auth where required; admin HTTP role does not imply database superuser authority |

A capability role may be omitted entirely if same-tree evidence proves the workload has no PostgreSQL dependency.

### P09.2 owner-to-capability mapping

P09.2 owner labels are semantic route owners, not necessarily PostgreSQL role names. The P09.3 contract therefore declares the mapping explicitly:

| P09.2 owner | P09.3 capability | Notes |
| --- | --- | --- |
| `auth` | `auth_runtime` | Auth API/admin login(s) |
| `catalog` | `catalog_runtime` | Catalog user/admin binaries |
| `progress` | `progress_runtime` | Progress service |
| `social` | `social_runtime` | Social domain APIs |
| `notifications` | `social_runtime` | Current notification read/read-all/retention routes live in `social-ts`; creation remains a worker exception |
| `reader` | `reader_runtime` | Reader reads plus derived trending writer |
| `scraper` | `scraper_runtime` | Scraper API/workers as supported by same-tree evidence |
| `media` | `media_runtime` | Current image/media API routes and media workers |
| `realtime` | `realtime_runtime` | Read-only runtime access |
| `database-protection` | `database_protection_api_runtime` | Current admin facade in `scraper-service`; may enqueue/cancel protection operations but cannot perform host-level restore/migration actions |

This mapping is audited. An unmapped current P09.2 owner with PostgreSQL access fails P09.3 validation.

## Workload login roles

Each deployed database-using workload receives a distinct login role and a role-specific DSN. The initial workload set comes from the current hybrid deployment and P09.1 scopes, including as applicable:

- `auth-service`
- `auth-admin`
- `catalog-go`
- `catalog-admin`
- `reader-go`
- `progress-go`
- `social-ts`
- `scraper-service`
- `scraper-batch-worker`
- `scraper-series-worker`
- `media-worker`
- `media-thumbnail-worker`
- `image-service`
- `notification-worker`
- `outbox-relay`
- `lifecycle-worker`
- `realtime-go`
- the KEDA PostgreSQL metrics identity

A workload gets one login role even when it belongs to more than one capability. Shared capability membership is preferred to password reuse. For example, the current `scraper-service` login may hold both `scraper_runtime` and `database_protection_api_runtime`, because both route families execute inside that process, while the host backup agent remains outside those runtime memberships.

Workers/services that do not query PostgreSQL do not receive a database credential simply because a neighboring workload has one.

## Grant derivation rules

### Request-driven writes

For every current route in `contracts/ownership/routes.v1.json` with a PostgreSQL `permitted_writes` entry:

1. the manifest owner maps to a P09.3 capability role;
2. that capability must include at least the declared table/action privilege;
3. the P09.3 contract must not grant a broader write action on that table unless a documented worker/technical exception requires it;
4. the P09.3 auditor fails when a current P09.2 write lacks a corresponding grant.

P09.2 remains authoritative for request-driven writes; P09.3 cannot silently reassign ownership.

### Read access

Read privileges are explicit but are not derived mechanically from every route dependency. They are documented at table/view granularity because a service can legitimately read a table without owning its writes. Reads must have same-tree source or acceptance-test evidence.

`SELECT ON ALL TABLES IN SCHEMA public` is prohibited for runtime roles.

### Sequences

Sequence `USAGE`/`SELECT` is granted only where inserts require an identity/sequence. Runtime roles do not get blanket sequence access.

### Functions

Function `EXECUTE` is explicit. Where transactional helpers such as `enqueue_event_outbox_v1` are the intended write boundary, producers receive function execution plus only the underlying table privileges required by the function's security model. P09.3 must not accidentally grant direct outbox delivery-state mutation to producers.

## Required narrow exceptions

### Notifications

- Notification Worker owns notification creation and dedupe receipt maintenance.
- Social may update notification read/acknowledgement state and execute declared retention/prune behavior.
- Social must not gain notification creation authority merely because it exposes notification read APIs.
- Notification Worker must not gain Social-owned read-state/retention mutation unless explicitly required and tested.

### Transactional outbox

- Domain producers may append events through the current transactional outbox contract.
- Outbox Relay alone may claim/update delivery metadata/state.
- Outbox Relay must not have generic domain-table mutation authority.
- Producers must not receive delivery-state update privileges.

### Lifecycle cleanup

- Authorized producers (for example Catalog/Scraper where current ownership requires it) may enqueue lifecycle cleanup intent/jobs transactionally.
- Lifecycle Worker alone receives execution/status/retry/delete authority for `lifecycle_cleanup_jobs`.
- Granting enqueue does not imply execution ownership.

### Foreign-key cascades

An authorized Catalog/Auth delete may cause declared database FK cascades. The parent owner does not receive direct `DELETE` on another domain's child table solely because PostgreSQL performs that cascade. Tests must distinguish parent-delete success from forbidden direct child-table delete.

### Derived trending

`series_trending_hourly` remains derived public trending data. Its current Reader analytics writer receives the minimum mutation privilege; Catalog receives only the read privilege it needs for presentation.

### Database protection and restore state

`database_operations`, `database_protection_runtime`, `database_restore_state`, recovery inventory/projection tables, and schema migrations remain technical protection/migration state. Application roles do not receive broad mutation rights to them. Only the protection/host authority and any explicitly documented runtime projection reader/writer get access.

### KEDA

KEDA receives a dedicated read-only login/capability over only the queue/status tables/views used by its PostgreSQL scaler queries. It gets no INSERT/UPDATE/DELETE, no schema ownership, and no general application-table read grant.

## Secret and DSN distribution

P09.3 extends, rather than bypasses, P09.1.

Each database-using workload gets a dedicated DSN env key, using existing service-specific keys where already present (`CATALOG_GO_DATABASE_URL`, `PROGRESS_GO_DATABASE_URL`, `SOCIAL_DATABASE_URL`, `READER_GO_DATABASE_URL`, `NOTIFICATION_DATABASE_URL`, `OUTBOX_DATABASE_URL`, `REALTIME_DATABASE_URL`) and dedicated keys for workers/services that currently consume broad `DATABASE_URL` or `POSTGRES_USER`/`POSTGRES_PASSWORD`.

P09.3 must remove broad `POSTGRES_USER`/`POSTGRES_PASSWORD` and generic bootstrap `DATABASE_URL` from application workload scope files when the replacement workload-specific DSN is wired and tested.

Role passwords are generated/persisted by the host-side deployment/bootstrap flow and written into the protected secret source used by P09.1. They are not committed to Git and are not printed to logs.

`create_workload_secret` continues to produce one Kubernetes Secret per workload. A role-specific DSN is rendered only into that workload's scope.

KEDA receives a separately scoped metrics DSN; it must not reuse the bootstrap `DATABASE_URL`.

## Role/grant reconciliation

P09.3 adds an idempotent host-side reconciliation step that runs:

1. after PostgreSQL is reachable;
2. after required migrations for the tree have completed;
3. before application deployments/rollouts are considered ready.

The reconciler:

1. validates the P09.2 ownership audit first;
2. validates `postgres-roles.v1.json` against its schema and same-tree tables/functions/workloads;
3. ensures capability roles exist with the runtime security baseline;
4. ensures workload login roles exist with the runtime security baseline;
5. rotates/sets workload credentials only through the protected secret source;
6. revokes broad `PUBLIC`/legacy application grants that would bypass the contract;
7. revokes obsolete capability memberships/grants;
8. reapplies the exact declared memberships and privileges;
9. verifies effective privileges from PostgreSQL catalogs;
10. fails closed if the contract cannot be reconciled.

The reconciler is declarative: removing a privilege from the contract removes it from effective access on the next reconcile. It must not only add grants.

## New-table/default-privilege rule

Runtime roles receive no blanket future-table access. The migration/bootstrap owner may continue owning newly created objects, but a new table/view/sequence/function is inaccessible to application runtime roles until the P09.2/P09.3 authorities are updated and reconciliation grants it explicitly.

This is intentional fail-closed behavior. A new migration that requires runtime access must update the ownership/grant contract in the same source milestone.

## Audit and verification

P09.3 adds a standard-library static auditor and a disposable PostgreSQL permission gate.

### Static auditor

The static auditor verifies:

- the P09.2 ownership audit passes first;
- all PostgreSQL resources in P09.2 exist in the P01/current schema inventory;
- every P09.2 request write is covered by a capability grant;
- every additional write grant has an explicit worker/technical exception and evidence;
- workload names correspond to current deployment/P09.1 scope files;
- no application workload is assigned the bootstrap credential;
- no runtime role is declared superuser/createdb/createrole/replication/bypassrls;
- KEDA is read-only;
- outbox producer/delivery privileges are separated;
- notification create/read-state permissions are separated;
- lifecycle enqueue/execution permissions are separated;
- all declared functions/tables/views/sequences exist in the current tree;
- duplicate/unknown role identities and unsupported privilege verbs are rejected.

### Runtime permission matrix

The runtime gate uses an explicitly supplied disposable PostgreSQL DSN, or Docker when available, and must never target an unqualified production database.

For every real runtime login role it proves:

- login/connect succeeds;
- at least one required read or write succeeds when the role has database work;
- representative forbidden cross-domain `INSERT`, `UPDATE`, and `DELETE` fail;
- `CREATE ROLE`, `CREATE DATABASE`, and schema/object ownership escalation fail;
- forbidden direct writes covered only by FK cascade fail;
- notification creation vs read-state boundaries hold;
- producer outbox append vs relay delivery-update boundaries hold;
- lifecycle enqueue vs execute boundaries hold;
- KEDA can execute only its required read queries;
- a newly created migration-owned table is unreadable/unwritable until explicitly granted.

Tests must exercise SQL directly and, where practical, the existing ORM/store path so a permissive ORM connection cannot hide a SQL-level mistake.

When Docker/DSN is unavailable, the runtime matrix is **blocked**, not passed. Static/source qualification may proceed with that blocker recorded, but P09.3 cannot be called runtime-qualified until the disposable PostgreSQL gate executes successfully.

## Deployment/readiness behavior

P09.3 itself does not implement P09.4 generation-aware readiness. However, deployment must fail before rollout if role/credential reconciliation fails or a required workload DSN cannot be rendered. No service may fall back from a missing narrow credential to the bootstrap credential.

The role contract is therefore installed before application rollout, but P09.4 owns the later readiness/generation enforcement semantics.

## Compatibility and migration strategy

1. Add and audit the P09.3 role contract while broad application credentials still exist in the protected host source.
2. Reconcile the runtime roles/grants in a disposable PostgreSQL environment and prove positive/negative permissions.
3. Generate/persist workload-specific DSNs.
4. Update each P09.1 workload scope and service config to require its narrow DSN.
5. Remove broad `POSTGRES_USER`, `POSTGRES_PASSWORD`, generic bootstrap `DATABASE_URL`, and broad KEDA DSN from Kubernetes application scopes.
6. Re-run ownership, secret-scope, permission, route, and deployment static gates.
7. Keep host migration/protection credentials available only to the host-side bootstrap/recovery path.

There is no compatibility mode in which a pod tries the narrow DSN and silently falls back to the old broad DSN.

## Non-goals

P09.3 does not:

- change route ownership or add routes;
- implement P09.4 ownership/readiness generation fences;
- implement P09.5 route/consumer denial;
- redesign service repositories around security-definer stored procedures;
- introduce row-level security unless an existing table already requires it;
- create a second secret-distribution mechanism;
- give runtime workloads database migration/protection authority;
- expand database access simply to make tests easier.

## Acceptance criteria

P09.3 is source-qualified when all of the following are true on one tree:

1. P09.2 ownership audit remains green with the same current-route authority.
2. The versioned PostgreSQL role contract and schema validate.
3. Static P09.3 audit finds no uncovered P09.2 PostgreSQL write and no undocumented extra write grant.
4. P09.1 workload secret scopes expose only role-specific DB credentials to database-using workloads and no broad bootstrap DB credential to application pods.
5. Grant reconciliation is idempotent and revokes obsolete access as well as granting required access.
6. Positive/negative permission tests exist for every real runtime role, including notification, outbox, lifecycle, FK cascade, trending, KEDA, and new-table fail-closed cases.
7. All runnable dependency-light/regression/ownership/route/secret-scope gates remain green.
8. The disposable PostgreSQL runtime gate is either freshly green or explicitly recorded as blocked by the environment; it is never inferred from static tests.
9. P09.4/P09.5 source remains untouched.
10. Source and tracker commits are separated and the mandatory all-refs Library durability gate completes before advancing.
