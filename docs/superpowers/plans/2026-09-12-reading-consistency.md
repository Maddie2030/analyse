## Shared protocol (binding for all tasks)

- GET `/api/progress/{series}/{chapter}` returns the **current series resume**; consumers MUST match `chapter_id` before restoring its page. An empty series has revision and session generation zero. All routes derive the account from authentication.
- POST `/open` accepts `{command_id: UUID, expected_revision: integer >= 0}`. Persist this intent before sending. Retries reuse its exact ID and revision. A successful open assigns a positive server `session_generation`, resets `command_sequence` to zero, advances `revision`, and selects the chapter without borrowing another chapter's checkpoint. A duplicate accepted open does not update recency. `/open` and `/commit` require `X-MReader-Account-ID` from the queued account scope and compare it with the authenticated user before target lookup; missing or different values return HTTP 403 `account_mismatch`. The header is a freshness fence, not identity. Progress reads enforce the comparison only when the header is supplied.
- POST `/commit` accepts `{command_id: UUID, session_generation: positive integer, command_sequence: positive integer, last_page: integer >= 1, scroll_position: number in [0,1], completed: boolean, completed_page: integer}`. `completed_page` is zero unless explicit end evidence has been observed, then the published page count. This keeps completion evidence independent of the current resume page when the reader scrolls back. Allocate a fresh UUID for every new command and persist the exact transmitted payload; timeout retries reuse it without mutation. Sequence numbers increase within an accepted session.
- Both commands return a flat canonical reading value with `series_id`, `chapter_id`, `last_page`, `scroll_position`, `updated_at`, `last_opened_at`, `revision`, `session_generation`, `command_sequence`, plus `accepted`, `duplicate`, `code`, and echoed `command_id`. `code` is `accepted`, `duplicate`, `revision_conflict`, `stale_session`, `stale_sequence`, or `command_conflict`. Conflicts return HTTP 200 with `accepted:false`, so clients retain and visibly pause the pending intent; no automatic new open/rebase. Validation is HTTP 400/422; missing/deleted targets 404; temporary storage errors 503; auth 401/403.
- A duplicate of the latest retained checkpoint identity/payload or retained per-chapter open identity is a no-op. The same retained sequence/ID with a different submitted payload conflicts, even if page clamping would produce the same stored checkpoint. The server keeps no permanent command log: an older exact retry is still fenced by revision/session/sequence, but a superseded ID reused with a new sequence/revision is outside its historical-uniqueness guarantee. Old sessions cannot replace resume or last-open. Exact completion from a recognized older chapter session may merge monotonically, but the response remains a conflict for its resume intent.
- IDs and server integers are bounded to JavaScript-safe values. Device timestamps are never server ordering keys. No normal runtime Redis progress flusher or progress cache authority.
- Social consumes a normal `reading_state_v1` view. Library adds `contract_version:1`, `generated_at`, `request_identity:{scope,state,sort,offset,limit}`, `recently_opened:{items,total}`, item `reading_revision`, `reading_available`, and `reading_action:{kind,chapter_id,chapter_slug}` or null. Recent items are global history, at most 12, from the same query as summary and main items. Existing fields remain.
