# RC4.85 P09.3 Restrictive Domain Grants Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Replace broad Kubernetes application PostgreSQL credentials with explicit workload login roles and reusable NOLOGIN capability roles whose effective privileges match the audited P09.2 ownership contract plus documented worker/technical exceptions.

**Architecture:** `contracts/ownership/postgres-roles.v1.json` is the declarative P09.3 policy. A standard-library auditor validates it against the same-tree P09.2 route manifest, current SQL objects, deployment workloads, and P09.1 scope files. A standard-library SQL renderer plus host shell reconciler uses the existing bootstrap credential to revoke/reapply exact privileges and persist workload-specific DSNs into the protected `.env`; `scripts/hybrid/deploy.sh` then renders only the narrow DSN allowed by each workload scope. Runtime services lose POSTGRES fallbacks, and an explicit DSN-or-Docker PostgreSQL gate verifies positive and negative privileges when a disposable database is available.

**Tech Stack:** PostgreSQL 16 SQL/psql, Python 3 standard library, Bash, existing Docker Compose hybrid stateful stack, Go/Python/TypeScript service configuration, JSON contracts, unittest/static regression scripts.

**Spec:** `docs/superpowers/specs/2026-09-16-rc485-p09.3-restrictive-domain-grants-design.md`

## Global Constraints

- P09.2 `contracts/ownership/routes.v1.json` remains the request-write authority and must pass `./scripts/run-ownership-route-audit.sh` on the same tree.
- P01 table disposition remains the table ownership/inventory authority; P09.3 does not create a competing ownership registry.
- Capability roles are `NOLOGIN`; workload identities are distinct `LOGIN` roles.
- Runtime roles are always `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`.
- The broad bootstrap credential remains host-only for migration, role reconciliation, recovery, and protected diagnostics.
- No Kubernetes application workload may receive broad `POSTGRES_USER`, `POSTGRES_PASSWORD`, or bootstrap `DATABASE_URL` after its narrow DSN is wired.
- Missing workload-specific DSN is a fail-closed configuration error; there is no fallback to bootstrap credentials.
- Runtime roles receive no blanket `ALL TABLES`, `ALL SEQUENCES`, or future/default privileges. A new table is inaccessible to runtime roles until explicitly added to the P09.2/P09.3 authorities.
- Reconciliation is subtractive as well as additive: it revokes obsolete memberships and grants before reapplying the exact contract.
- P09.4 readiness/generation enforcement and P09.5 route/consumer denial remain out of scope.
- When no disposable PostgreSQL DSN and no Docker runtime are available, the runtime permission gate reports BLOCKED and is not counted as passed.
- Source and tracker/handoff commits remain separate; the all-refs Library durability gate must complete before P09.4 begins.
