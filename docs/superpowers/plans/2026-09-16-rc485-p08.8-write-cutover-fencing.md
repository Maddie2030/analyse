# RC4.85 P08.8 Write/Cutover Fencing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make production database restore installation/source/generation bound, retention-pinned, phase-journaled, interruption-recoverable, and safe against replay of stale restored work while preserving the single existing restore engine.

**Architecture:** Keep `database_operations`, the canonical local recovery store, and `backup-agent.sh` authoritative. Add a host-owned restore-control record plus v2 external phase journal under the canonical recovery root; mirror the committed generation into PostgreSQL, bind admin/CLI confirmation to source+installation+generation, and selectively terminalize replay-unsafe restored work before writes resume.

**Tech Stack:** Bash, PostgreSQL SQL migrations, FastAPI/asyncpg, React/TypeScript, unittest/static regression scripts, existing local recovery store and Docker Desktop hybrid deployment.

**Spec:** `docs/superpowers/specs/2026-09-16-rc485-p08.8-write-cutover-fencing-design.md`

## Global Constraints

- Preserve the single canonical `database_operations` queue, local recovery store and backup-agent restore engine.
- Preserve opaque `bkp_<24 hex>` source selection and P08.3–P08.7 bridge/facade/import/retention/catalog/drill boundaries.
- Destructive restore confirmation must bind exact source public ID + source SHA-256 + installation fingerprint + expected restore generation.
- Host restore control is authoritative when PostgreSQL is offline/replaced; PostgreSQL holds only a runtime mirror.
- Drills must not enter production journal/generation/stale-work paths.
- Do not globally flush Redis or RabbitMQ; reconcile only MReader-owned replay-unsafe durable work.
- Do not begin P09 work.
